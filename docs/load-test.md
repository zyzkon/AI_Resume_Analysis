# 压测报告

对容器化环境跑的两轮压测。第一轮确定**能撑多少、先从哪里崩**；第二轮是修复后
的复测。中间有一段走错路的过程，保留在文档里，因为那次错误比第一轮的发现更值钱。

日期 2026-11-14。

## 环境

| 项 | 值 |
|---|---|
| 宿主 | Windows 11，24 逻辑核 |
| Docker Desktop | 分到 **8 核 / 7.76 GiB**（WSL2 后端） |
| 被测服务 | `docker compose` 起的 7 个容器，api 为 uvicorn **单进程** |
| worker | Celery prefork，`--concurrency 4` |
| 数据库 | MySQL 8.0（同机容器），`max_connections=151` |
| 缓存/队列 | Redis 7（同机容器） |
| 压测客户端 | locust 2.47，跑在**宿主机**，经 Caddy `:8080` 打进来 |
| 模型 | `LLM_PROVIDER=mock`（固定耗时，不烧钱，测的是系统本身而不是上游 API） |

客户端和被测服务同机，CPU 会互相抢，所以下面所有数字**偏保守**，生产环境只会更好。

## 方法

三个约定，决定了数据可不可信：

1. **全部用 mock**。真实模型一次 30~90 秒，压测时会瞬间堆几百个任务，测出来的是 DeepSeek 的排队时间，不是这套系统的吞吐。
2. **所有虚拟用户共享一个预取的 token**。第一版脚本让每个用户 `on_start` 自己登录，结果 200 个用户同时跑 bcrypt，API 的 40 个线程全被登录占死，业务接口只能分到 12 rps —— 测的是密码哈希的吞吐，不是接口容量。改成预取 token 后数据才干净，登录单独用 `--tags login` 测。
3. **按接口分组**（`--tags poll|trend|login`），因为不同接口的瓶颈完全不同，混在一起看平均值得不到结论。

复现：

```bash
# 造数据，输出 LOAD_TOKEN / LOAD_RESUME_ID / LOAD_ANALYSIS_ID
eval "$(python tools/prepare_load_test.py | grep '^export')"

# 读接口
locust -f tools/locustfile.py --headless -u 100 -r 10 -t 60s \
       --host http://127.0.0.1:8080/api --tags poll --only-summary

# 登录（bcrypt）
locust -f tools/locustfile.py --headless -u 50 -r 5 -t 40s \
       --host http://127.0.0.1:8080/api --tags login --only-summary

# worker 消化速度
python tools/burst_submit.py 600
```

## 第一轮的诊断（一半是对的）

200 并发那一轮整个系统塌了，P98 直接跳到 **30000 ms**。日志里的原因是：

```
sqlalchemy.exc.TimeoutError: QueuePool limit of size 10 overflow 20 reached,
connection timed out, timeout 30.00
```

**30 这个数字不是巧合，是 `pool_timeout=30`。** 链条：

```
200 并发请求
  └─> anyio 线程池上限 40（FastAPI 跑同步路由的默认值）
        └─> 每个请求要一个 DB 连接，池只有 10 + 20 = 30 个
              └─> 池先耗尽，后来的请求只能排队
                    └─> 一旦请求变慢（trend 要 576ms），排队立刻堆积
                          └─> 等满 30 秒 → 抛 TimeoutError → 500
```

当时得出的两个结论：

**① 线程数 > 连接数，是配置错误。** 池上限 30、anyio 默认 40 线程，多出来的 10 个线程注定拿不到连接。**结论：应该让连接池 ≥ 线程池。**

**② 有 CPU 密集的接口混在里面。** `GET .../trend` 每次要把 50 条历史分析的 `result` JSON 反序列化再逐条做 Pydantic 校验，P50 610 ms、吞吐只有 poll 的 43%。它占住一个连接 576ms，是 poll（83ms）的 7 倍。

佐证是容器资源：200 并发那轮 **api CPU 峰值 458%**（8 核里吃掉 4.6 核），而 worker 只有 0.8%、mysql 8.7%。瓶颈完全在 API 进程内部，跟队列和数据库无关。

**第 ① 条是错的。** 下一节就是它怎么被证伪的。

## 走错的一步：把两个池对齐，结果更糟

按第 ① 条改：`pool_size` 10 → 20（池上限 40），同时把 anyio 线程池也显式设成 40，让两个数字由代码保证相等（`app/db/session.py` 里 `align_thread_pool()`）。

| 场景 | 并发 | 请求数 | 失败 | 吞吐 | P50 | P95 |
|---|---|---|---|---|---|---|
| `GET /analyses/{id}` | 100 | 15111 | 0 | 254 req/s | 65 ms | 140 ms |
| `GET /analyses/{id}` | 200 | 2401 | **289 (12.04%)** | 42 req/s | 230 ms | 20000 ms |

**失败率从 1.96% 涨到 12%。** 连接池更大了、线程也对齐了，为什么更差？

### 真因：两个池之间的死锁

加一个临时探针（`/debug/pool`，验证完已删）在 200 并发时读内部状态，饱和的那一刻是这样的：

```
thread_limit=40  thread_borrowed=40  |  Checked out connections=40  Pool size=20 Overflow=20
```

线程借满了，连接也拿满了，而报错的堆栈停在：

```
File "/app/app/api/deps.py", line 98, in get_current_user
    → db.get(User, ...)  →  pool.connect()  →  TimeoutError
```

如果 40 个线程各自拿着 40 个连接在干活，就根本不该有人再要连接。所以真实情况是：
**有一部分连接被「此刻并不占用线程」的请求held着。**

机制在这里 —— FastAPI 处理「同步依赖 + 同步路由」的请求，分**三次**进线程池：

```
① solve_dependencies  → get_db 建 Session（不连库）→ get_current_user 查库【拿到连接】
② 路由函数            → 复用同一个 Session（连接一直held着）
③ 依赖清理            → db.close()【这里才归还连接】
```

第 ① 步结束时线程立刻归还，但连接没有。于是：**在途请求（占着连接）可以多于线程数。**
当这样的请求多了，连接被抽干；而新进来的线程要连接、要不到，就在 `pool.connect()` 里等 5 秒 —— 线程被这些"等连接"的请求占满，连接被那些"等线程"的请求占着，两边互等，直到超时。

**这就是为什么「线程数 = 连接数」不成立**：它不是两个独立参数碰巧相等，而是一条流水线上两类资源在中间有个缺口。把数字对齐只是把缺口挪了个位置（30 → 40），缺口本身还在。

## 修复：在请求这一层设闸

正确的不变量是「**同时在处理的请求数 ≤ 线程数 < 连接数**」，而限制点必须在请求进入线程池**之前** —— 也就是 ASGI 层。

新增 `app/core/concurrency.py`：一个纯 ASGI 中间件，`anyio.Semaphore(30)` 把并发的请求挡住，多余的留在事件循环里排队（不占线程、不占连接）。配套三处：

| 改动 | 目的 |
|---|---|
| `MAX_CONCURRENT_REQUESTS = 30` | 闸门宽度，同时决定线程池容量（启动时 `align_thread_pool(30)`） |
| `DB_POOL_SIZE 20 + MAX_OVERFLOW 20 = 40` | 必须比闸门宽：给「占着连接但没占线程」的请求留位置 |
| 启动校验收 `MAX_CONCURRENT_REQUESTS ≤ db_max_connections` | 两个数分居两处，改一个忘一个的话故障只在满负荷时出现 |
| `/health` 豁免闸门，并改成 `async def` | 它不碰数据库；被排队会让 healthcheck 3 秒超时而误判容器死亡 |

三层关系落到代码里是：**闸门 30 ≤ 线程池 30 < 连接池 40**。

**没有任何秒级、十秒级的尾巴。** 修复前 200 并发下 P98 = 30000 ms，修复后 100% 分位是 631 ms。

### 混合流量（10:4:2:1）

100 并发、45 秒：**8411 请求，0 失败，189 req/s**

注意 trend：修复前 P50 **610 ms**，修复后 **170 ms**。它没改一行代码 —— 变快是因为线程不再互相踩（40 个线程抢 8 个核的 GIL，比 30 个线程慢得多）。这条顺带证明"多加线程不会更快"。

### 闸门内部的实测状态（300 并发时采样）

| 指标 | 观测值 | 上限 |
|---|---|---|
| 闸门内在途请求（`gate.in_flight`） | 峰值 **30** | 30 |
| 线程池已借出（`borrowed_tokens`） | 8 ~ 19 | 30 |
| 已 checkout 的数据库连接 | 14 ~ 23 | 40 |

三个数都没顶到自己的上限，压测结束 5 秒内全部归零 —— 说明不是"擦着临界线过关"，是真的有余量。同一时刻的连接数稳定在 20 出头，也解释了为什么 MySQL `max_connections=151` 完全不是问题。

## 结论

- **单实例容量约 260 req/s**（`GET /analyses/{id}`，8 核 / 单 uvicorn 进程 / mock 模型），100 并发下 P95 140 ms。
- **超过容量后是排队，不是报错**：300 并发仍然 0 失败，只是 P50 从 57 ms 涨到 760 ms。这是有意的设计 —— 宁可慢，不要 500。
- **最先崩的从来不是数据库**。修复前后 MySQL 都只用了 14~23 个连接（上限 151）、CPU 8.7%。崩的永远是 API 进程内部的资源编排。
- **worker 不是瓶颈**。mock 下能跟上 109 任务/秒的灌入速度；真实模型下按单次 45 秒算，4 并发约 5.3 任务/分钟 —— 那才是需要扩容的地方。
- **登录 26 req/s 是设计使然**：bcrypt 单次约 250 ms，40 个线程并发时单次涨到 1.4 秒（抢 8 个核），吞吐 ≈ 40 / 1.4 ≈ 28。登录本来就不该是高频接口。

## 还能做什么（按收益排序，均未实施）

1. **`uvicorn --workers 2~4`**：多进程各自持有独立的闸门和连接池。这是唯一能真正提高吞吐的手段（GIL 决定了单进程到头）。代价：连接数 × 进程数，4 × 40 = 160 超过 MySQL 的 151，得同时把 `DB_POOL_SIZE` 调小或调 `max_connections`。
2. **给 trend 减负**：`limit=50` 改成默认 20，或对 `result` 做列裁剪（现在 SELECT 整行，JSON 字段很大）。它仍是 CPU 密集路径，压它的耗时等于放大所有读接口的容量。
3. **登录限流**：26 req/s 的容量配一个按 IP 的滑动窗口，防止有人用登录接口打 CPU。
4. **长期方案**：把接口改成 `async def` + 异步驱动（asyncmy），请求全程不换线程，那个"连接被held在阶段之间"的缺口会从根上消失，闸门就能省掉。改动量大，收益在当前规模下不明显。

## 局限

- **mock 模式**：worker 的真实瓶颈（等模型 30~90 秒）在这轮压测里完全没被触发，相关结论是估算而不是实测。
- **同机压测**：locust 和被测服务抢同一台机器的 CPU，真实客户端在外部时数字会更好。
- **Docker Desktop 的端口转发**（WSL2 用户态代理）在 200 并发以上本身也可能成为瓶颈之一，没有单独隔离验证。
- **只有单实例**，没有测多副本 + 负载均衡；闸门是按进程算的，多副本时总并发 = 30 × 副本数，要重新核连接数。
- **闸门会放大慢客户端的影响**：整个请求（含响应发送）都在闸门内，一个卡住不读响应的连接会占一个名额。真实浏览器不会这样，但公网环境值得加一个发送超时。
